# Lessons: test harness, smokes, guards, verification

Read before touching `tools/*_smoke*`, `tools/headless.js`, any guard, or before running a negative test. Each entry is a past incident; text is verbatim.

## Two traps (from project/STATUS.md)

- **The parent page is gated.** Anything touching the parent area in a test must answer the question first. `tools/offline_smoke.mjs` has `unlockParentGate(h, label)` for this and calls it at **both** parent visits — the page is navigated to twice and the gate is per load. The pre-existing parent checks use `.click()`, which bypasses hit-testing, so they would pass even with no gate at all; `parent_smoke.js` now asserts reachable state (`offsetParent === null` **and** `elementFromPoint`).
- **A mouse-driven harness cannot see touch bugs.** `headless.js` has no touch emulation, so any `touch-action`-class defect stays green until a real finger finds it. Assert the computed style for anything drag-related.

## Footguns (moved verbatim from AGENTS.md)

- **Never undo a verification mutation with `git checkout`/`git restore`/`git reset`/`git stash` — that resets the file to HEAD and silently destroys the work under test (task 223, near-miss).** Verifying a guard means mutating the artifact (flip a colour, drop a selector), running the check, then putting it back. Those commands do **not** put back the working copy — they put back the **last commit**, so on a file holding this task's uncommitted edits they wipe the edits. Here `game/shared/accessibility.css` (the whole V6.2 block) and `game/pages/classroom.html` were reverted to HEAD mid-verification; only a re-read of `git status --short` caught it, and the lost block had to be retyped. **Snapshot to a temp path first (`Copy-Item <file> $env:TEMP\<name>.bak`), mutate, run, then restore from that copy and confirm with a hash compare — never from git.** The rule covers every "restore the tree" shortcut (`git stash pop`, `git apply -R`, force checkout): if the tree may hold uncommitted work, copy first, because you otherwise cannot prove what you did not lose. Corollary: after any destructive verification batch, re-run `git status --short` — a file you expect to be `M` that has dropped off the list is the damage signal.
- **A validator that regenerates what it inspects proves nothing** (R5). The tell is a check labelled "deterministic" or "fresh" that shells out to the *writer*. `check_release.js` was the worst case: its "syntax" step called `check_all.js` (the whole 24-tool battery), it ran `sync-docs.sh` (rewriting all of `docs/`) and `build_offline.js` — so a stale artifact could never be reported, only quietly fixed. It now fingerprints `docs/`, the cache list, the manifest and the ZIP before and after and fails if it changed anything: the read-only contract is enforced, not promised. Same family as the candy `showHint` global collision and the phantom manifest self-entry — the failure is always a check that cannot fail.
- **CI was red on all 25 runs and nobody could see why — a log is evidence, a guess is not (task 177).** GitHub Actions' job-log endpoint returns `403` unauthenticated even for a public repo and the HTML page says "Sign in to view logs", so "read the log" was impossible without `gh` (`gh auth login --web` runs a detached device flow, which works from this host). Once authenticated the cause was obvious in one read: `ocean_smoke.js` printed **zero lines for the full 10-minute step timeout**, because `cdp()` resolved only on `ws.onopen` with no `onerror` and no timeout, so a refused DevTools websocket hung the process forever instead of failing. **An unbounded await is a check that cannot fail.** `headless.js` now bounds the connect (15 s), every CDP command (30 s) and each `/json/version` request (2 s), runs the handshake inside the existing retry loop, and adds `--disable-dev-shm-usage` + `--remote-allow-origins=*`. Separately, `ci.yml` ran `node tools/<smoke>` **raw**, bypassing the 0-check boot-crash retry that both `run_all.js` and `check_fast.js` apply — the only asymmetry in the repo, and the reason 19/26 legs went red while `hub_smoke` in the un-contended `fast` job never once failed. Never trust that a green local run means CI can see the same thing. When a harness step hangs, compare the step's own duration against the constant that bounds it (`BOOT_ATTEMPTS × BOOT_POLL_TRIES × BOOT_POLL_MS` = 24 s matched the 26 s jobs exactly).
- **Never run a `*_smoke` tool raw in CI — `run_all.js` IS the boot-crash retry, and Chrome boot crashes are routine (task 181).** On run #40, **13 of 27 matrix legs** hit `Chrome did not start (debug port N) after 4 attempts ... no assertions ran` with the browser process still **alive** (`exited=false`) and stderr empty — it never opened the debug port — and **all 13 passed on the retry**. `Release QA` ran `node tools/offline_smoke.mjs` **raw**, the last asymmetry in this repo, so it inherited no protection and went red on **every** run. Two traps when fixing this: (a) routing it through the runner was **not sufficient** — the retry condition was `pass === 0 && fail === 0`, and `offline_smoke` prints 3 PASS lines before it boots a browser, so it must also honour `headless.js`'s own `no assertions ran` marker; (b) `run_all.js` rejected `.mjs` positional names outright. Keep the battery at 27 — pass the filename explicitly rather than joining the battery. **And `offline_smoke.mjs` had no exit code at all**: it exited 0 while printing 3 FAILs, so a blocking release gate could only go red by *crashing*, never by *failing*. A gate with no exit code is the most dangerous kind of "check that cannot fail". Corroboration for `gh` now working: the job-log endpoint needs `gh`; `gh api .../jobs/<id>/logs` rejects with "terminal escape sequences" — use `gh run view <id> --log`.
- **A guard that asserts something its own implementation can never satisfy will red a real pipeline (task 180).** `guards/games_map_negtest.js` claimed "every per-game smoke is reachable via pages or game files", but `audio_buses_smoke` covers `game/shared/audio-buses.js` and is reachable from **neither** — `mapFileToSmokes()` routes every `game/shared/*` edit to `BROAD()`, the whole battery. Its coverage was real; the *claim* was wrong, and the false red took down `Release QA` on CI runs #34 and #37, masking the Offline E2E failure on both. **The wrong fix is to add a mapping to `run_all.js` to satisfy a check that is itself wrong** — that invents a mapping which does not exist and hides the real defect. Fix the check, and **guard the exclusion list itself** (the `BROAD()` fallback must still exist; every excluded name must be a real file), or the list becomes a place to hide a genuinely unreachable smoke. Any guard run by CI should be executed locally at clean HEAD first — this one had been failing since R15 and was only discovered by accident.
- **A diagnostic that can describe the wrong process is worse than no diagnostic (task 178).** The CDP failure message `describe()` builds is the *only* record of why the browser went away — so it is a check like any other, and it needed its own guard. It read the boot loop's shared `chromeExitEvent`, which **every** attempt writes (including a failed attempt's child still winding down) and which is **never cleared** when a later attempt succeeds, so `browser=Chrome exited code=0` could be naming a corpse from attempt 1 while the live browser was healthy. Run #39's Offline E2E failure turned on exactly that clause. **The exit record must be per-attempt (`let exitEvent` inside the loop) and the "still running" branch must name the live pid**; `chromeExitEvent` stays only for the boot-failure report. `tools/guards/chrome_diagnostic_negtest.js` pins it. **And the guard's first version passed against the code it was written to catch**: its assertion was behavioural, and which of `describe()`'s two truthful branches appears depends on whether the socket close or the child `exit` event lands first. Pin the deterministic invariant (which binding the code can reach); demote the racy observation to supporting evidence. Two more self-inflicted vacuity traps in the same test: attaching `.catch()` to the in-flight `evalp` made the rejection *handled*, so the absorber never printed and the assertion could never fire — **the absorber only speaks for unhandled rejections**; and a loose regex matched the separate `[headless] Chrome exited while a CDP session was open:` line, so the test read a different message than it thought. **Note also that an idle socket death is silently swallowed** — a reproduction needs work in flight.
- **Do not apply the fix proposed in GitHub issue #3.** It recommends "add connection retry logic" and offers "fix or remove this test". Both regress: the CDP handshake is *already* inside the `BOOT_ATTEMPTS` retry loop (another retry layer cannot help a socket that dies **mid-session**, the observed shape), and `offline_smoke.mjs` is the only gate that proves offline playability — it found 3 real product bugs in R6. **Release QA was the sole red job (run #39: 27/30 green, matrix fully green), with a root cause that stayed unknown when this was written — RESOLVED by task 204 (2026-10-06), see below.** Why it stayed unknown: the step log was unreadable from the Linux host — GitHub's job-log endpoint returns `403` unauthenticated even for a public repo, check-run annotations are empty, and `gh` is not installed here. The two unconfirmed leads are now closed: (a) "task 177d's absorber appears not to have fired (no `[headless] Unhandled CDP failure:` line, yet the run died as a fatal Node crash)" — answered by task 204: the absorber only covers *un-awaited* (unhandled) rejections, and a dropped socket inside an `await`ed command throws as an uncaught exception through the `.mjs` tool's top-level await, which the absorber never sees; `headless.js` now has a matching `uncaughtException` net and `run_all.js` retries a zero-FAIL mid-session CDP death as environmental; (b) "`ci.yml` runs `offline_smoke.mjs` **raw**" — obsolete since task 181.
- Test over HTTP (Live Server), not `file://` — file:// breaks audio, the kitty iframe, and throws Unsafe-attempt warnings. **racing3d is the ONLY ES-module game**: under `file://` Chrome CORS-blocks `racing3d.mjs`, so the page shows its HUD but never boots (`window.__r3d`/`startRacing3D` absent). Symptom "opens from hub in Chrome but not starting" = the hub was opened via `file://`; direct Live-Server open works because it's HTTP. Always open `game/index.html` via Live Server too.
- **A fixed `sleep(N)` in a smoke buys N ms of *simulated* time only while a frame costs less than 50 ms.** `racing3d.mjs`'s rAF loop does `Math.min(clock.getDelta(), 0.05)`, so the clamp never binds at 60 fps — but on a software-WebGL runner measured at 113 ms/frame (worst 183 ms) it binds on every frame and the game runs at **~41% of wall-clock speed**: 15 frames delivered 700 ms of sim for 1700 ms of wall clock. Every `await sleep(N)` in `racing3d_smoke.js` therefore under-bought on CI while passing locally, which is how `steering`, `kart banks` and `reactive decor` went red on the runner and green on the dev host with **identical game code**. Fix: `r3d.haltLoop(true)` + `r3d.step(1/60)` × N, which delivers the exact sim budget on any host (batches 4–9 already did this). Measure the delivered sim time before believing a physics assertion — `avgFrameMs` is wall-clock only.
- **A `SKIP` is not a `PASS`.** If a check cannot run because the *environment* lacks a capability, record it with `skip(name, why)` from `tools/headless.js` so it prints `SKIP` and is counted. Never convert reduced coverage into a green battery, and never stub the hook the test is asserting on.
- **This host can be killed on a resource spike (Acode sandbox on a phone).** opencode runs inside the Acode app, which appears to enforce CPU/RAM failsafe limits that kill the process outright. Long single runs are therefore not trustworthy: several `check_all` / `run_all` invocations in tasks 152–153 were killed mid-run with no output. **Work in small batches and keep runs resumable** — `node tools/run_all.js --concurrency 2 --resume` (or `--sequential` for heavy tools), default checkpoint dir `$TMPDIR/run_all_resume`. Never re-run a whole battery because one was killed; resume it. Lower the concurrency before blaming a test. This is also why the heaviest tool is split into four shards (`touch_interruption_{a..d}_smoke.js`) rather than one 85-check process.
- **Validate with the smallest relevant command — do not run the full battery for a small change.** A one-line UI change (hiding the parent area's ZIP link) is covered entirely by `parent_smoke.js` (~6 s). Running all 24 tools for it cost several minutes, got the run killed twice by this host, and produced four *red* entries that were not real failures at all (they were the tools I had terminated mid-flight: `fail=0` with a boot-crash retry). **A red tool with `pass=N fail=0` is a crash, not a failed assertion** — check whether you killed it before believing it. The full `check_all.js --docs --offline` ritual is for release/commit boundaries and broad refactors, not for a scoped fix.
- **Check for orphaned Chrome before believing any "it only fails under load" story.** `headless.js` used to terminate Chrome only through Windows `pwsh`, so on Linux every smoke run **leaked its browser**; the `catch` swallowed the failure and `close()` reaped nothing. 21 orphans accumulated in one session and starved later runs — `touch_interruption_smoke` went from hanging on its first game for 8+ minutes to **85/85 in 100 seconds** once they were reaped. Cleanup now uses the exact `ChildProcess` handle on Windows (with the exact-profile `pwsh` match as fallback) and POSIX `pkill -f user-data-dir=<tag>`; `close()` waits for the debug port to go quiet before profile removal or another browser starts. The Windows process-handle path cut measured close time from a 2448 ms median to 52 ms average (task 156). **If the suite suddenly gets slow, or a check "only" fails under parallelism, run `pgrep -f chromium | wc -l` before editing the test** — several "load flakes" in task 152 were this leak, not flaky assertions.
- **A passing smoke proves the assertions ran — not that a child can reach the control.** `element.click()` bypasses hit-testing, so a `.click()`-driven smoke passes happily while the real control sits off-screen or under another element. The explorer's `#char-modal` had no CSS at all and rendered its hero buttons at y≈1093 in a 700px viewport (clipped by `#app{overflow:hidden}`) — the game was unplayable and `kitty_smoke` was green for years. **When a test stands in for a human interaction, assert the geometry too**: fully inside the viewport *and* `document.elementFromPoint(centre)` resolves to the intended element. This is the task-120 anti-pattern in a second shape — not a stub, but a test exercising a path no child can use.
- **`scrollIntoView` inside a harness *rescues* geometry that is genuinely broken** (task 177c). `headless.js`'s `boxOf` calls `scrollIntoView({block:'center'})` before measuring, so a control clipped below the fold inside an `overflow:hidden` container gets scrolled in and passes — while a child still cannot see it. The explorer's `◀ ▶ 🐾` controls had no positioning and rendered after the 100%-height canvas, so they were below the fold at **every** viewport; `offline_smoke` passed locally because the clamp landed the button exactly at the fold, and only failed on CI because the `pulse` scale sampled `bottom = innerHeight + 1` on that run. The fix is to assert the layout, not to trust the scroll: also note that a **fixed `sleep(N)` hoping the rAF loop ticked** is the same class of mistake — `driving_smoke`'s `steering` check read zero movement under CI load and passed on the dev host with identical game code, so it now pauses the loop and steps `update()` deterministically.
- **Never let a test race layout, navigation, or an animation.** Four checks flaked only under parallel load, and in every case the honest fix was a *readiness wait* (poll until the condition that means "the work has been applied" holds), never a longer sleep and never a loosened assertion. Real cases: a `.click()` handler that navigates via `location.href` (wait for the landed page, not a fixed 300 ms); an element removed by a Web Animations `onfinish` (900 ms animation vs a 1000 ms sleep — 100 ms of margin, gone under load); pieces positioned in JS (wait until they are sized and at distinct positions, *then* assert "no overlaps", so the assertion can still fail). Distinguish a **readiness wait** (poll on a condition unrelated to the assertion) from a **retry-until-pass** (polling the assertion itself, which makes it vacuous).

## From CONTRIBUTING.md (some overlap with the entries above; kept verbatim)

- **Never run a `*_smoke` tool raw in CI.** Chrome boot crashes are routine on GitHub runners (13 of 27 legs hit one on run #40, all recovered on retry). `node tools/run_all.js <smoke>` is the retry that absorbs them; `Release QA` was the last runner bypassing it and went red on every run until task 181. Also note `tools/run_all.js` cannot route a tool that has no exit code — check `offline_smoke.mjs`'s `getFails()` if you add a new standalone gate, since a gate that prints FAIL and exits 0 is worse than no gate.
- **A guard that asserts something its own implementation can never satisfy will red a real pipeline (task 180).** Run every CI-run guard locally at clean HEAD before believing it.
- **A diagnostic is a check too, and it needs its own guard.** The first version of `guards/chrome_diagnostic_negtest.js` **passed against the code it was written to catch**, because its assertion was behavioural against a race (whether the CDP socket close or the child `exit` event lands first). When a guard's premise can only be true by luck, pin the deterministic invariant (which binding the code can reach) and demote the flaky observation to supporting evidence.
- **A layout that "passes" because the harness scrolls it into view is still broken** (task 177c). `headless.js`'s `boxOf` calls `scrollIntoView`, so a control clipped out of the viewport inside an `overflow:hidden` container gets scrolled into view and its geometry check passes — while a child still cannot see or tap it. When a test stands in for a human interaction, assert the geometry too, and remember that an animated control (e.g. a `pulse` scale) can tip a marginal check over only on some runs.
- **The parent area is behind a question gate** (task 201, at the user's request): a multiplication question guards the offline download, the update check, progress reset and audio test, so a small child cannot reach them. Anything that drives the parent page in a test **must answer the gate first** — `tools/offline_smoke.mjs` provides `unlockParentGate(h, label)` for this and calls it at **both** parent visits, because the tool navigates to the page twice (online to prime the cache, offline to prove the controls survive) and the gate is per page load, not remembered. Do not "fix" a gate failure by deleting the gate or forcing a button visible: the offline gate exists precisely to prove those controls are genuinely reachable once unlocked. Note the pre-existing parent checks use `.click()`, which bypasses hit-testing and so passes even when the gate is absent — `parent_smoke.js` asserts reachable state (`offsetParent === null` **and** `elementFromPoint`) for that reason.
- **`headless.js` drives real mouse input only and has no touch emulation**, so any `touch-action`-class defect stays green until a real finger finds it — task 200 shipped a broken sorting drag for exactly this reason. For anything draggable set `touch-action:none` on the draggable element itself (`touch-action` on `html,body` does not cover children) and assert `getComputedStyle(el).touchAction === 'none'` in the smoke.
- **A check that reads state *after* an interaction cannot see a bug that the interaction itself fixes.** Task 216: `puzzle_smoke.js` asserted the exact level-label string, but read it *after* clicking `#sceneButton` — whose handler `startPuzzle()` calls `setGrid()` → `updateLabels()`. The `[object Object]` defect existed only in the window between page load and that first click, so the assertion passed while the label was broken. **Read state before any interaction when the bug may be in the initial render.** Same family as the task-177c `scrollIntoView` rescue: the test's own setup can erase the defect it is meant to catch.
- **A count that pins today's value cannot survive the change it is supposed to allow.** This bit five times in one session: `classroom_smoke`'s `SW.tiles === 11`, `hub_smoke`'s games count of `10`, `coloring_smoke`'s `U.palette === 11`, `offline_smoke`'s `===3` sequencing step pin, and `sequencing_smoke`'s hardcoded 4-id sequence list. Derive the expectation from the data (`SERBIAN.*`, `app-registry.js`, the game's own `ids()` API, `run_all.js --list`) and assert the **invariant** — "slots and cards are equal and non-zero", "the numbers render in the vocabulary's order", "every sequence id builds" — rather than the literal.
- **Negative-testing a guard means mutating the artifact it checks — restore it from a copy, never from git (task 223).** To prove a guard can fail, temporarily change the thing it inspects (flip a colour, drop a selector), run the guard, then put it back: `Copy-Item <file> $env:TEMP\<name>.bak` first, mutate, run, `Copy-Item` the backup back, and hash-compare both. `git checkout -- <file>` / `git restore` / `git reset --hard` / `git stash` reset to **HEAD**, so on a file carrying this task's uncommitted edits they destroy the very change under test (this happened to `game/shared/accessibility.css` in task 223). After a destructive batch, re-run `git status --short` — a file you expect to be `M` that has vanished is the damage signal.
