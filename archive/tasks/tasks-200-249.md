- 200. DONE — Fix touch dragging in sorting + sequencing (user-reported). (Completed 2026-10-05, Ponytail Lazy Dev.)
    - **User report:** the sorting game's drag (red→red, animals→animals) does not work. Confirmed as a real product bug, not a flake.
    - **Root cause:** both draggables left `touch-action` unset. The drag is implemented with pointer events, and when a draggable element does not declare `touch-action:none`, a **touchscreen** browser claims the gesture for panning/zooming and fires `pointercancel` part way through — so the item stops following the child's thumb and the drop never lands. With a mouse this never happens, which is why every smoke stayed green.
    - **Why no test caught it:** `tools/headless.js` drives real **mouse** input only — it has no touch emulation (its only `Emulation` call is `setDeviceMetricsOverride` with `mobile:false`). A finger-only defect is invisible to the entire battery by construction.
    - **Fix:** `touch-action:none` plus explicit `user-select:none` on `.sort-item` (`game/pages/sorting.html`) and `.seq-card` (`game/pages/sequencing.html`). Sequencing had the identical latent gap and was fixed in the same pass.
    - **New checks assert the COMPUTED style**, which is the only way to pin a CSS-level touch contract without a touch-emulating runner: `sorting_smoke` asserts `getComputedStyle('.sort-item').touchAction === 'none'` and `user-select === 'none'`; `sequencing_smoke` asserts the same for `.seq-card`.
    - **Proved non-vacuous:** with `touch-action` reverted on both pages, the checks went red with the exact offending values — `.sort-item` computed `manipulation`, `.seq-card` computed `auto`. Restored, `sorting_smoke` **21/21** and `sequencing_smoke` **15/15**.
    - **Correction recorded rather than repeated:** I initially assumed `touch-action` is not an inherited property and wrote that into a comment. Measurement contradicted it — `.sort-item` computed `manipulation` (from the page's `html,body` rule) while `.seq-card` computed `auto`. Only the verified facts are kept in the smoke comments, and the assertion is on the value (`none`) rather than on a theory about why it was wrong.
    - **Ruled out while investigating:** the user's other report about a highlight that persists after the image changes is **not** sorting — `sorting.js:281` calls `setSelected(null)` in `newRound()`, and `setSelected` removes the class from the previously selected element, so the selection ring is cleared correctly.
    - **Still open, needs user clarification:** (a) the request to present the options "under a mathematical question like 4x6=__", and (b) "the presenting window sometimes does not show all on smaller devices", and (c) which game has the stale yellow highlight around a chosen answer. None of these could be attributed to a specific page with confidence, and guessing would risk changing the wrong game.
